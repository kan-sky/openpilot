# Navdy USB-First Bluetooth Fallback

## Scope

The user requested wireless Comma/Navdy display and navigation exchange while
retaining USB: disconnect USB to use Bluetooth, reconnect USB to return to USB.
No phone relay, hotspot, global Bluetooth reset, vehicle command publisher,
model/control change, automatic pairing or bond removal is added.

The test target is the existing Comma on AGNOS 19.8-carrot-bt1 and Android API22
Navdy. The APK is an update of the user's existing v157, not a replacement of
phone, ambient or power functionality. Exact signed v158 SHA256:

`534379839fc6ef3e66be844472531267939f57a1b7aa13836be090cc7c64b8a5`

Signer SHA256, unchanged from v157:

`afe4eff90076c92ed8e087ec49a5d7257f5d473916243daafb16dc41e8b40bcf`

## Transport And Freshness

- Direct USB remains the existing ADB/TCP transport and is always attempted first.
- A configured, explicitly bonded Bluetooth peer is the first fallback. Paired
  Jetson relay candidates remain available if wireless is absent or unavailable.
- During Bluetooth or Jetson operation, one background USB probe opens a candidate without
  sending display data. The main loop closes Bluetooth before writing to USB.
- Every successful USB exchange resets fallback ordering, so the next cable loss
  cannot begin with a stale Jetson candidate from an earlier handover.
- A legacy-compatible inactive bootstrap completes SSH/remote ADB readiness before
  constructing the first active Jetson snapshot. No new remote handshake protocol
  or Jetson-side update is required by that change.
- The full existing display snapshot is sent at a target 5Hz, compressed with
  zlib level1. Navigation/camera feedback uses the existing Navdy sources. Source
  identity, sequence and freshness are not regenerated by the transport.
- One in-flight transaction and one pending Android-main callback, maximum32KiB
  raw/wire payloads, strict UTF-8/JSON/finite-value checks and CRC prevent queue
  growth and malformed frames. There is no image stream.
- A receiver-issued lease bounds display age to500ms without synchronized clocks.
  Receipt and main-thread dispatch both validate it. Success ACK follows actual
  main-thread application, not enqueue. The Comma response deadline is650ms.
- The capture timestamp is taken before snapshot construction, not at socket
  entry. A sender pause cannot rejuvenate an old snapshot; sender age at or above
  500ms is rejected before transmission, as are future timestamps.
- A50ms main-thread watchdog clears only expired Bluetooth-owned state. USB has
  priority, and an old session cannot clear newer USB/Bluetooth state. A blocked
  Android main thread can delay clearing; dispatch still rejects expired frames
  when it resumes. IO watchdog and reconnect backoff are separately bounded.

See [the protocol](../tools/navdy/WIRELESS_PROTOCOL.md). Existing navigation
reader expiry/validation remains in force; link success alone is not valid TBT
or navigation-driven speed-control evidence.

## Provisioning And Rollback

Both devices need their existing approved bond. Comma reads a private
`/data/navdy/bluetooth.json` with boolean `enabled` and the exact Navdy `peer` MAC.
Navdy reads only the exact Comma MAC from app-owned mode0600
`/data/data/com.navdy.hud.app/files/openpilot-bluetooth-peer`.
Do not put keys, pairing secrets or device-specific configuration in Git.

The APK uses secure authenticated RFCOMM. The Comma requests and checks medium
Bluetooth security; neither side scans or pairs automatically. On this already
supported OS, the existing radio service is enabled via its existing flag.
Discoverability and pairability stay off. No OS flash was performed for this work.

Absent/disabled Comma configuration preserves USB and paired Jetson behavior.
Removing/disabling it ends a wireless session without resetting the global radio.
To roll back the app, retain the exact v157 APK and current app data/signing key.
Do not uninstall the app or clear its phone/ambient pairing data.

## Native Verification

The Comma was freshly verified offroad, no ignition and no controls allowed before
each intervention. Only the managed Navdy bridge was restarted after selective
source installation. No Comma reboot or model/control restart was requested.

The first APK installation ran out of Navdy data-partition space. An old temporary
APK was moved to the existing cache partition, preserving it, and the new APK was
installed with `pm install -r`. The command exceeded the initial client timeout
while Android was optimizing DEX. Subsequent PackageManager path, new app PID and
SHA256 of the actual installed APK confirm successful completion. Do not treat a
client timeout as proof of install failure or overwrite the system priv-app.

Initial three software USB-detach/reattach cycles succeeded. A90s Bluetooth phase
had447 distinct display snapshots, median RTT46.05ms, p95 92.53ms and maximum
170.57ms; all883 sampled link states were fresh/connected. The repeated transitions
exposed unnecessary23-25s Jetson attempts. That observed ordering defect was fixed
before final testing; those timings are not the final handover result.

A subsequent USB return failed even though the kernel enumerated the Navdy.
`fuser` identified an idle preexisting ADB5037 server owning its USB interface;
the production ADB5038 server saw no devices. The other server had only Navdy,
no forwards and no connected clients. It was stopped once after the offroad
guard; USB recovered automatically without restarting the bridge. Production
code does not kill arbitrary ADB servers. Use the existing5038 server for future
diagnostics instead of starting a competing default5037 daemon.

The kernel also emitted `ACL packet for unknown connection handle` diagnostics
while native Bluetooth acknowledgements remained fresh. Their underlying cause
was not established here; passing these bounded application tests does not prove
the OS radio is free of faults.

not total radio/Android resources or an onroad geometry/model/DM workload. All

## Remaining Boundaries

Software USB deauthorization exercises actual socket loss, USB enumeration,
native secure RFCOMM and the production APK; it is not a physical cable test.
Offroad payload acknowledgement is not full moving geometry/radar workload,
optical panel confirmation or proof of phone-to-navigation-control integration.
No-USB cold boot and sustained real phone/ambient coexistence require their own
actual-device evidence. Never infer these from a connected flag alone.
